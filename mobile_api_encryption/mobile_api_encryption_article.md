# HTTPS를 쓰는데 API 데이터까지 암호화해야 할까?

> 모바일 앱과 API 서버의 고정 키, 동적 파생 키, 공개키 기반 세션 합의를 비교하며

모바일 앱과 서버 사이의 데이터를 보호하려고 할 때 가장 먼저 떠오르는 것은 HTTPS다. 그런데 TLS를 이미 사용하더라도 요청과 응답의 JSON을 한 번 더 암호화해야 할지 고민하게 된다.

결론은 조건에 따라 달라진다. **HTTPS가 보호해야 할 구간을 충분히 감싸고 있다면 추가 암호화는 필수가 아니다.** 반면 TLS를 종료하는 중간 시스템에는 원문을 보여주지 않고, 지정된 업무 서버에서만 복호화해야 한다면 애플리케이션 계층의 암호화가 의미를 가질 수 있다.

이 글에서는 그 필요성을 먼저 구분한 뒤, 세 가지 접근을 비교한다. 구현은 [실행 안내](README.md), 패킷과 운영 정책은 [상세 설계](mobile_api_encryption_design.md)에서 확인할 수 있다.

**GitHub 코드와 문서:** [모바일 API 데이터 암호화](https://github.com/devmakermin/BackendEngineeringNotes/tree/main/mobile_api_encryption)

## 1. 알고리즘을 고르기 전에 복호화 지점을 정한다

TLS는 통신 양 끝 사이의 기밀성과 무결성을 제공하고 서버 인증을 지원한다. 하지만 TLS 연결이 종료된 뒤 애플리케이션이 다루는 평문까지 자동으로 보호하지는 않는다. [OWASP TLS Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html)

```mermaid
flowchart LR
    A["앱: JSON 암호화"] -->|"HTTPS"| B["프록시: TLS 종료"]
    B -->|"내부 TLS + 암호문"| C["지정 서버: 본문 복호화"]
    C --> D["업무 처리"]
    D --> E["로그 · DB · 내부 서비스"]
```

이 구조에서 프록시는 암호화된 본문을 전달한다. 지정 서버는 평문을 볼 수 있으므로, 그 서버의 접근 권한과 이후 처리 경로를 여전히 신뢰해야 한다.

| 보호하려는 상황 | 먼저 검토할 수단 |
| --- | --- |
| 공용 네트워크에서 도청·변조 방지 | 올바르게 설정한 HTTPS와 인증서 검증 |
| 프록시와 API 서버 사이의 통신 보호 | 내부 TLS 또는 필요에 따른 mTLS |
| TLS 종료 프록시에도 특정 본문을 공개하지 않기 | 프록시와 분리된 복호화 권한 및 애플리케이션 암호화 |
| 로그·APM에서 민감 데이터 제거 | 수집 최소화, 마스킹, 평문 기록 제한 |
| DB·백업 유출에 대비 | 저장 암호화, 키 접근 통제, 보관 정책 |
| 변조된 앱·탈취된 계정의 악성 요청 차단 | 인증·인가, 입력·업무 규칙 검증, 남용 탐지 |

본문 암호화로 URL, 헤더, 길이, 호출 시점까지 전부 숨겨지지는 않는다. 여기서 말하는 노출 대상은 TLS를 종료하는 중간 시스템 등이다. HTTPS가 유지되는 구간의 외부 관찰자는 TLS로 보호되는 HTTP 내용을 그대로 읽을 수 없다.

## 2. 방식 A — 고정 대칭키를 공유한다

앱과 서버가 같은 AES 키를 가지고 JSON을 암호화하면 구조는 단순하다. AES-GCM을 사용하면 본문의 암호화와 함께 인증 태그로 변조 여부를 확인할 수 있다.

문제는 **배포된 모든 앱에 같은 비밀키를 넣는 경우**다. 앱 패키지에서 키를 찾아내거나 실행 중 키 사용을 관찰할 수 있다면, 하나의 유출이 같은 키를 공유하는 전체 범위에 영향을 준다. 난독화만으로 이 공통 비밀값을 안전한 서버 자격증명처럼 취급할 수는 없다. [OWASP MASWE-0004](https://mas.owasp.org/MASWE/MASVS-STORAGE/MASWE-0004/)

여기서 ‘고정 키’라는 단어만으로 모든 설계를 동일하게 판단해서는 안 된다. 안전한 등록 절차를 통해 장치마다 다른 키를 공급하는 구조는 공통키 하드코딩과 다르다. 다만 그 경우에도 등록·저장·폐기·교체가 필요하다.

플랫폼 키 저장소는 중요한 선택지다. 그러나 키의 추출을 어렵게 하는 것과 공격자가 장악한 앱 프로세스에서 키를 사용하지 못하게 하는 것은 다르다. Android 문서도 프로세스가 침해되면 키의 추출 없이 키를 사용할 가능성을 설명한다. [Android Keystore](https://developer.android.com/privacy-and-security/keystore)

## 3. 방식 B — 요청마다 다른 키를 유도한다

처음에는 다음과 같은 형태를 생각할 수 있다.

```text
사용자 식별값 + 서버 시각 + 요청 순번
→ 복잡한 난수 패턴
→ 요청별 암호화 키
```

하지만 입력과 알고리즘을 공격자도 알 수 있다면 같은 결과를 만들 수 있다. 값이 요청마다 달라져도 비밀이 생기지는 않는다. WELL 같은 통계적 의사난수 생성기나 공개 입력의 해시를 암호학적 비밀값의 대용으로 사용해서는 안 된다.

필요한 것은 **충분한 엔트로피를 가진 실제 비밀값**이다. HKDF는 그 비밀값에서 목적에 맞는 키를 유도하는 데 사용한다. `salt`와 `info`는 공개될 수 있으며, `info`는 용도와 문맥을 구분한다. HKDF가 비밀값을 전달하거나 서버 신원을 확인해 주는 것은 아니다. [RFC 5869 §2–3](https://www.rfc-editor.org/rfc/rfc5869.html#section-2)

이 예제의 선택은 다음과 같다.

```text
sessionSecret = ECDH(내 임시 개인키, 상대 임시 공개키)
sessionSalt   = SHA256(서명이 검증된 핸드셰이크 문맥)
info          = [프로토콜 버전, 세션 ID, 사용자 참조값, 통신 방향, 순번]
messageKey    = HKDF-SHA256(sessionSecret, sessionSalt, info, 32 bytes)
```

서버 발급 시각은 핸드셰이크 문맥에, 메시지 시각은 AAD에 포함한다. 매번 시각을 비밀키의 재료처럼 취급할 필요는 없다. 이 구분은 시간 검증과 키 유도의 책임을 읽기 쉽게 한다.

요청별 파생도 항상 필수는 아니다. 방향별 세션 키와 유일한 nonce로 구성할 수도 있다. 이 예제에서는 질문의 ‘요청마다 다른 키’를 확인하기 위해 순번별 파생을 선택했다.

또한 하나의 세션 비밀값에서 모든 요청 키를 유도한다면, 그 비밀값이 유출되었을 때 해당 세션의 키들이 함께 영향을 받는다. **키가 매번 바뀐다는 이유만으로 과거 메시지 보호나 침해 후 복구가 자동으로 확보되는 것은 아니다.**

## 4. 방식 C — 공개키로 세션 비밀값을 합의한다

②는 결국 ‘최초 비밀값을 어디에서 얻는가?’라는 질문을 남긴다. ECDH는 양측이 공개키를 교환해 같은 비밀값을 계산하게 해 준다. 하지만 상대 공개키가 누구의 것인지 확인하지 않으면 중간자가 자기 키를 대신 전달할 수 있다.

교육용 예제는 다음 순서로 이 문제를 드러낸다.

1. 앱이 임시 ECDH 키쌍과 무작위 nonce를 만든다.
2. 서버가 기존 로그인 결과로 사용자를 확인한 뒤 임시 키쌍과 세션 ID를 만든다.
3. 서버가 양측 공개키·nonce, 사용자 참조값, 세션 수명, 버전·알고리즘을 함께 서명한다.
4. 앱이 **응답 밖에서 이미 신뢰한 서버 검증 공개키**로 서명을 확인한다.
5. 양측이 ECDH 비밀값을 계산하고 HKDF로 방향·요청별 키를 유도한다.
6. AES-GCM으로 요청과 응답을 보호한다.

서버의 서명 공개키와 ECDH 공개키는 역할이 다르다. 전자는 신원을 검증하고, 후자는 세션 비밀값을 합의한다. 서명 개인키는 서버에 남고, 공개 검증키는 비밀일 필요가 없다.

신뢰키를 핸드셰이크 응답에서 함께 받아 그대로 믿으면 인증 문제가 해결되지 않는다. 특히 TLS 종료 프록시를 신뢰 대상에서 제외하려면 그 프록시가 검증키까지 바꿔치기할 수 없는 신뢰 경로가 필요하다.

이 절차는 자체 프로토콜을 배포하라는 제안이 아니다. 운영에서는 검토된 표준과 구현체를 우선 평가해야 한다. HPKE는 관련 암호 구성의 선택지이지만, 공개키의 진위·API 로그인·완전한 재전송 방지·양방향 세션 정책을 모두 대신하지 않는다. [RFC 9180 §9.7–9.8](https://www.rfc-editor.org/rfc/rfc9180.html#section-9.7)

## 5. AES-GCM에서 빠뜨리기 쉬운 두 가지

첫째, **같은 키와 nonce의 쌍을 재사용하지 않는다.** 이 예제는 방향과 순번으로 메시지 키를 나누고, 순번을 12바이트 nonce로 인코딩한다. 따라서 같은 세션의 송신 채널을 복제하거나 재시작 뒤 순번을 초기화해서는 안 된다. GCM의 IV 유일성은 핵심 요구사항이다. [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)

둘째, **본문이 사용되는 문맥도 인증한다.** 암호문이 정상이어도 다른 API 경로나 다른 요청의 응답으로 옮겨 쓰이지 않게 해야 한다. AAD에는 메서드·경로/쿼리·세션·방향·순번·시각을 넣고, 응답에는 상태코드와 원요청 순번도 넣는다. AAD는 암호화하지 않지만 변조 검증에 포함한다.

수신 측은 실제 HTTP 요청과 대기 중인 요청에서 문맥을 구성해야 한다. 클라이언트가 패킷에 주장한 경로만 신뢰하면 실제 라우트와의 결합이 사라진다.

Node.js에서는 `decipher.update()`의 결과를 업무 처리에 먼저 넘기지 않는다. 인증 태그의 검증이 완료되는 `decipher.final()`이 성공한 뒤에만 사용한다. [Node.js Crypto](https://nodejs.org/api/crypto.html#deciphersetauthtagbuffer-encoding)

## 6. 올바른 암호문도 다시 전송할 수 있다

공격자가 정상 요청의 암호문을 그대로 재전송하면 GCM 태그는 여전히 유효하다. 타임스탬프는 오래된 요청을 거르는 데 도움이 되지만, 허용 시간 안의 중복 요청까지 없애지 못한다.

수신 과정은 다음처럼 분리한다.

```text
입력 크기·인증 사용자·세션·시각 확인
→ GCM 태그 검증과 JSON 해석
→ 세션·방향·순번을 원자적으로 예약
→ 인가·업무 규칙 확인과 처리
```

위조 요청이 정상 순번을 먼저 소비하지 못하도록 재전송 기록은 태그 검증 뒤에 쓴다. 여러 API 서버는 공유 Redis에서 `SET ... NX`와 만료를 하나의 명령으로 적용할 수 있다. [Redis SET](https://redis.io/docs/latest/commands/set/)

다만 `EX 300`만 복사해 넣어서는 충분하지 않다. 기록이 사라진 후에도 같은 메시지가 시간 정책상 허용된다면 다시 처리될 수 있다. 이 예제는 메모리 기록을 세션 만료까지 유지하며, 분산 설계에서는 노드·Redis 시계 차이와 상태 유실까지 다룬다.

**재전송 차단과 멱등성도 다르다.** 요청 예약 뒤 서버가 중단되면 업무가 수행되지 않았을 수 있다. 반대로 업무는 끝났지만 응답만 유실되었을 수도 있다. 결제·주문 API에는 업무별 멱등성 키와 원자적인 결과 저장이 별도로 필요하다.

## 7. 세 방식을 같은 기준으로 비교하면

| 기준 | 앱 공통 고정 키 | 비밀값 + HKDF | 인증된 임시 ECDH + HKDF |
| --- | --- | --- | --- |
| 비밀값의 출처 | 앱과 서버에 미리 넣은 동일 키 | 별도 등록·배포·합의 과정 | 양측의 임시 개인키 |
| 요청별 키 분리 | 별도 설계 필요 | 가능 | 가능 |
| 모바일 배포본의 공통 비밀키 | 포함하면 추출 위험 | 설계에 따라 다름 | 불필요 |
| 핵심 관리 대상 | 공통키 배포·회수 | 최초 비밀값과 파생 문맥 | 신뢰키·핸드셰이크·세션 수명 |
| 실패하기 쉬운 지점 | 한 번의 유출이 넓게 전파 | 공개값만으로 키를 만듦 | 신원 검증 없이 공개키만 교환 |
| 관계 | 비교 대상 | 키 유도 구성 요소 | 비밀값 합의와 키 유도를 결합 |

실제 구현에서 가장 큰 비용은 AES 호출 한 줄이 아니다. 신뢰키를 어떻게 갱신할지, 앱이 백그라운드에서 복귀했을 때 세션을 어떻게 재합의할지, 다중 서버가 세션과 중복 기록을 어떻게 공유할지가 운영 복잡도를 만든다.

## 8. 내가 먼저 확인할 질문

1. 보호 대상이 전체 본문인지 특정 필드인지 정했는가?
2. TLS 종료 시스템 중 누가 원문을 보면 안 되는가?
3. 복호화 서버와 키 관리 권한을 실제로 분리할 수 있는가?
4. 모바일 키 사용, 서버 키 교체, 세션 만료·폐기 경로가 있는가?
5. 중복 요청·재시도·장애 시 업무 결과를 일관되게 다룰 수 있는가?

이 질문에 답하기 전에는 암호화 계층만 하나 더 추가해도 보호 범위가 분명해지지 않는다.

**암호화 규칙을 복잡하게 만드는 것보다, 비밀값을 어떻게 합의하고 보관·교체하며 어느 지점에서 복호화하는지가 더 중요하다.** 추가 암호화는 그 경계가 실제로 필요할 때 선택할 수 있는 수단이다.
